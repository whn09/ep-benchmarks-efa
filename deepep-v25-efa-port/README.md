# DeepEP V2.5 + EFA port

deepseek-ai/DeepEP `main` (V2.5, `93eb6eb`) does not run on AWS EFA as is. The port of the
amazon-contributing/DeepEP EFA changes (the unordered hybrid kernels, GIN signal budget,
PR #18's cached-dispatch fix) onto it is the branch
[`whn09/DeepEP@amazon-v2.5`](https://github.com/whn09/DeepEP/tree/amazon-v2.5) (`f501cd1`).

Result on 4 x p6-b200 (EFA installer 1.50.0, GIN type 5): **at parity with amazon main
`6de427b`** at 2N and 4N, and the full `test_ep.py` sweep (36 configurations) plus a 20-seed
pressure test passes on 4N with no Xid.

## What it takes

| | why |
|---|---|
| NCCL **2.32.3** | V2.5 uses 2.32-only API (`NCCL_WIN_GIN_ONLY`) and checks the runtime version; 2.31 does not work |
| aws-ofi-nccl **master** (`cb0c85e`) | NCCL 2.32 asks the EFA-GDA plugin for `backendVersion 2`; the 1.21.1 in installer 1.50.0 supports 0..1, so `devCommCreate` fails with `unsupported backendVersion 2 (plugin supports 0..1)`. v2 support is `452f302` (2026-09-11), in no release yet |
| EFA-GDA **device** backend in the JIT | V2.5 compiles only `NCCL_GIN_GDAKI_ENABLE=1` (EFA_GDA=0). On EFA the device code then reads the EFA-GDA QP/CQ with the mlx5 layout: Xid 13/31 at address 0 in the first dispatch. The branch enables EFA_GDA (and drops GDAKI) when `NCCL_GIN_TYPE`/`EP_GIN_TYPE` is 5 |
| `NCCL_CUMEM_HOST_ENABLE=0` | with 2.32.3 the torch NCCL `all_to_all` in test_ep's reference path fails `ncclCuMemHostAlloc ... out of memory` on GPUs 4-7 (not DeepEP) |
| `libdw-dev` + https rewrite | DeepJIT submodule needs elfutils; its `.gitmodules` URL is ssh |

What the port changes, besides re-applying the amazon files under V2.5's renames
(`elastic` -> `ep`, `WorkspaceLayout` -> `EPWorkspaceLayout`, `kNumTMAAlignmentBytes` = 32):

- `comm::Context` picks GDAKI only when supported and `NCCL_GIN_TYPE` is unset (V2.5 asserts
  GDAKI); the unordered GIN layout is an opt-in ctor flag used by `EPBuffer` only, so the
  bucket/engram/PP buffers keep upstream requirements.
- V2.5's GIN barrier signals slot `rank_idx` on all N ranks (amazon used N-1 compact slots),
  so the signal-budget assert is `>= num_rail_ranks`, not `>= num_rail_ranks - 1`.
- The unordered combine has a proxy warp (block is not whole warpgroups), so V2.5's
  `warpgroup_reg_realloc` picks `dec` for the forward warps' 216 registers and ptxas rejects
  it; explicit `warpgroup_reg_alloc/dealloc` are restored for that kernel.
- `EP_HYBRID_KERNEL=ordered` still selects upstream's kernels (wrong on EFA, kept for IB).

## Build

```bash
cd ../deepep-v2-efa-official && ./build_image.sh sm100 && cd -     # base: EFA 1.50.0, CUDA 13.3.1
docker build -f Dockerfile --build-arg BASE=deepep-v2-efa-official:sm100 \
  --build-arg DEEPEP_REF=f501cd1babf9d9d6629ddb3cee84bf8917ddb6e8 -t deepep-v25-efa:sm100-f501cd1 .
```

## Run (on every host, only NODE_RANK differs)

```bash
NODE_RANK=0 MASTER_ADDR=<node 0 private ip> WORLD_SIZE=4 ./run_test_ep.sh
```

## Results (`results/summary.md`, generated by `parse_test_ep.py`)

Per run: mean over all ranks; runs alternate arms on the same nodes. 8192 tokens, hidden 7168,
top-8, 256 experts, 24 SMs, FP8 dispatch, alignment 128, `async_with_compute_stream=0`.
Both arms ran in one environment (NCCL 2.32.3 + aws-ofi-nccl `cb0c85e`); `amz` = amazon main
`6de427b` (`tests/elastic/test_ep.py`), `v25` = this port (`tests/ep/test_ep.py --defer-epilogue=0`;
`a69d830` at 4N, `f501cd1` at 2N, which differ only in the GIN-disabled path).

| µs (mean of runs) | 2N amz | 2N v25 | 4N amz | 4N v25 |
|---|---:|---:|---:|---:|
| dispatch | 1506.8 | 1503.9 | 3897.8 | 3896.7 |
| cached dispatch | 1500.4 | 1498.3 | 3871.7 | 3869.7 |
| combine | 2836.7 | 2831.9 | 7351.1 | 7348.5 |
| combine reduce epilogue | 68.4 | 68.4 | 107.3 | 107.4 |

**Measurement trap.** V2.5's `test_ep.py` defaults to `--defer-epilogue=1`, so its
`--test-first-only` case is `async_with_compute_stream=1`, while amazon's first case is `=0`.
Compared that way the reduce epilogue looks 48-54% slower (1N 234 vs 158 µs) — pure upstream
V2.5 shows the same 234 µs; with `--defer-epilogue=0` it is 161 vs 158 µs. Single rank-0 lines
mislead too: 2N combine reads 2733 vs 2912 µs on rank 0 but 2836.7 vs 2831.9 averaged.
