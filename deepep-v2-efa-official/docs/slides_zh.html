DeepEP V2 on AWS EFA

原理 · 安装 · 性能 · 四条待合 PR

  • MoE all-to-all（dispatch + combine）跑在 EFA 上，而非 IB / RoCE
  • 只用发布包：不编 NCCL、不编 aws-ofi-nccl、不换内核模块
  • 后端：两个环境变量，decode dispatch 365.1 → 169.4 µs（2.16×，2 节点）
  • 补丁：PR #8+#9 再把 decode 一层 348.8 → 273.0 µs（-21.7%，2 节点）
  • 叠加：四个 PR 合并后 decode 一层 350.4 → 256.2 µs（-26.9%，另一条 campaign）

数据：results/p5en_3arm_20260831/（158 份日志，139 条断言由 check_comparison.py 校验）、results/p5en_2n4n_20260825/（8 个 cell 与其 summary.txt 交叉核对）、results/p5en_stack_20260831/ 与 results/p5en_ovlp_20260831/。各 campaign 的代码 SHA 与机器不同，每个比值只在本 campaign 内取，未相乘。全部数字在构建时由日志算出。

结论速览

  1. 后端：decode dispatch 2.16×（2 节点）、5.44×（4 节点）；prefill 1.09×。默认配置走 CPU proxy。
  2. PR #8+#9：2 节点 decode 一层 -21.7%（348.8 → 273.0 µs）。唯一同时改善 dispatch 与 combine，也是唯一在 prefill 有效的臂（2 节点 -9.9%）。
  3. PR #1+#2 须配 EP_NUM_SUB_PARTS=1：4 节点一层 -3.2% → -6.4%，与 PR #8+#9 打平；仅改善 dispatch。
  4. 四个 PR 可叠加，但是"各取其优"而非求和：decode 一层 350.4 → 256.2 µs（-26.9%）；combine 完全相加，dispatch 残差 +47.5 µs = 较大单臂收益的 85% —— 两条 PR 打的是同一块 dispatch 成本。
  5. --prefer-overlap-with-compute 把 #8+#9 拆成两半：两处未被该 flag 门控的改动占 decode dispatch 收益的 74%、prefill combine 收益的 34%。
  6. PR #8 的 node 偏斜机制只在 2 节点成立：per-node combine 偏斜 9% → 1.8–3.8%；4 节点三条臂同为 10–11.5%。
  7. 补丁收益随规模衰减，衰减倍数取决于测在哪个配置（4.5× / 2.5×）。

均为同硬件、同命令行、臂间交错的 main-vs-patch 比较。方法与明细见第 8–16 节。

1 · DeepEP V2 是什么

  • MoE 的 GPU all-to-all 内核：dispatch 把 token 路由到 expert，combine 收回
  • 内网后端 NVSHMEM → NCCL GIN：CUDA kernel 直接发 RDMA，不经 CPU proxy
  • 统一 ElasticBuffer API；SM 数解析式给出，不再 auto-tune
  • 显存随 num_max_tokens_per_rank 线性缩放：128 tok ≈ 1.6 GB/GPU，8192 tok ≈ 100 GB/GPU

p5en / p6-b300 均为 EFA 网络，需要专门的 GDA 通路，IB 上的结论不能直接套用。

2 · EFA-GDA 依赖链

GDA = GPU Direct Async：NIC 的 WQ 映射进 GPU 显存，kernel 自己写 64 B WQE 并 ring MMIO doorbell，CPU 全程不介入。

4 · GDA 与 CPU proxy 的路径差异

栈发送路径每 rank CPU 代价
DeepEP V1 + NVSHMEM (EFA)kernel → NVSHMEM proxy 线程 → libfabric → NICCPU 唤醒 + syscall + verbs
UCCL-EPkernel → 4 个 Rust proxy 线程/rank → ibverbs → NIC4 线程/rank，32 线程/节点
DeepEP V2 + GDAKI (type 5)kernel 写 64 B WQE + ring MMIO doorbell（FI_EFA_GDA_OPS）0 线程

延迟：省掉 CPU 唤醒 + syscall + verbs 三段。规模弹性：CPU proxy 的 handoff 按链序列化，GPU 把 N 个 flush 分给 N 个 thread。这就是上一页的差距在 4 节点（5.44×）大于 2 节点（2.16×）的原因。

8 · Campaign 与验收口径

NODES="P5EN-1 P5EN-2" ./run_campaign.sh
  • Reps 轮转：一 rep 跑完所有 cell 再进下一 rep，慢漂移不会被误认成 arm 效应
  • 每个 cell 独立 MASTER_PORT；日志名自带全部变量（arm / 节点数 / SM / tokens / knob / debug / GIN 后端 / rep / node）
  • 全 rank 池化：combine 按机器分层，单节点均值最多偏 11%（第 15 节）
  • 离群 rep 显式排除：偏离本 cell 中位数 25% 以上才排除，日志保留并在 AUDIT 中打印
  • ./verify_run.sh logs/*.log → no FAILs；check_comparison.py 从日志重算全部 139 条断言

口径固定项：--test-first-only ⇒ 全部数字为 FP8 dispatch @ expert_alignment=128；--ignore-local-traffic 关 ⇒ SO GB/s 含机内流量、非线速，故以时间为指标；EP_BUFFER_DEBUG 关（它在 dispatch 计时循环内 printf）。

"各取其优"，不是求和。combine 上 residual -0.3 µs —— PR #1+#2 在那儿本就为 0，叠加直接拿到 #8+#9 的 combine；dispatch 上 residual +47.5 µs = 较大单项收益的 85%，两组打的是同一笔 dispatch 开销。净收益相对两条单臂各 -10.9% / -6.6%。

划分按 op 变，这才是结论。decode dispatch：45.8 µs 的收益里无门控的两个占 74%（33.8 µs）。prefill redComb：562.2 µs 的收益里被门控的两个占 66%（370.1 µs）。prefill dispatch 两个取值都是平的。

17 · 跨栈对比的口径

V1 / UCCL-EP / V2 的横向数字见 README.md § Side-by-side results。该节的行组是不同 shape、不同时钟（2026-05/BF16 的 4096 tok 组 vs 2026-08/GDAKI 的 8192 tok FP8 组），不可按列比较，故此处不复制成单表。

跨栈对比前须对齐三项：

  1. 口径：DeepEP 把每个 op 拆成 2 个 kernel，只引 1 个会系统性偏低
  2. 字节分母：per-selection 记账把 DeepEP 在 2 节点高估 4×、4 节点 2×，足以反转 scaling 结论
  3. 时间与带宽并列：仅给 GB/s 会反转结论，须同时给 µs 并说明分母

第 9–16 节的 main-vs-patch 为同硬件同命令行，不受上述影响；但不可读作"与 IB 上的官方 DeepEP 打平" —— 官方的 prefer_overlap_with_compute 取值不同。

18 · 四个坑

  1. 版本号不是判据：同名 aws-efa-installer-1.50.0.tar.gz 内的 aws-ofi-nccl 可能是 1.21.1（有 ncclGinPlugin_v14）或 1.20.0（无）。以 nm 的符号为准。
  2. hostname 会解析出 link-local IPv6，rendezvous 报 errno 22。用私网 IPv4。
  3. docker run 须加 --init：PID 1 为 python 时不 reap 子进程、signal 转发不可靠，卡在 rendezvous 的 worker 会成为孤儿并持续占用 MASTER_PORT。
  4. GDAKI context 不能与另一进程共用同一张 EFA 网卡：常驻的 DeepEP-v2 容器即使 GPU util 0% 也持续持有 GIN context，第二个进程在 ElasticBuffer 构造时报 fi_enable failed: Cannot allocate memory。空闲显存与 util 均无法判断此项；第几个 local rank 失败才是有效信号。
