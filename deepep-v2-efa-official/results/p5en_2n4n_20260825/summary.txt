DeepEP-v2 on EFA / p5en.48xlarge -- 2-node and 4-node campaign, 2026-08-25
==========================================================================

HEADLINE
--------
The 8-10% prefill-dispatch gap and a 2.1x decode gap between our published
2026-08-13 numbers and the released `ec623f3` image are NOT a code difference.
They are a *GIN backend selection* difference, controlled by two env vars:

    NCCL_GIN_TYPE=5  NCCL_SYM_GIN_KERNELS_ENABLE=0

With the packaged EFA installer 1.50.0 stack, `libnccl-net-ofi.so` registers
TWO GIN plugins -- a Libfabric proxy-assisted one (type 2) and Libfabric_GDAKI
(type 5). Both are loaded; NCCL picks type 2 by default. Forcing type 5 gives:

    2N / 12 SM / 8192 tok  dispatch  1655 us -> 1500.2 us   (74.0 -> 81.5 GB/s SO)
    2N / 12 SM /  128 tok  dispatch   352.0 us ->  168.9 us  (2.08x)

This RETRACTS the claim in docs/runbook_zh.md ~L424 that after installer 1.50.0
none of the "route B" env vars are needed. They are not needed for GDAKI to
*load*, but they ARE needed for it to be *used*.

MECHANISM (from NCCL_DEBUG=INFO, logs/gin_plugin_selection_*.grep.txt)
----------------------------------------------------------------------
Both arms print:
    GIN/Plugin: Loaded gin plugin Libfabric_GDAKI (v14)
    GIN/Plugin: Successfully loaded external plugin .../libnccl-net-ofi.so
The type-5 arm additionally prints:
    GIN/Plugin: Skipping plugin Libfabric index 3 type 2: NCCL_GIN_TYPE=5 requested
i.e. a *second*, type-2 Libfabric GIN plugin exists at plugin index 3 and is
what the default env selects, even though GDAKI loaded fine.

Why NCCL_GIN_TYPE=5 ALONE crashes -- the log names the reason:
    gin/gin_host.cc:229 (ncclGinValidateSignalRequest)
      NCCL WARN GIN strong signals are required, but the GIN plugin does not
      support them.
    gin/gin_host.cc:440 (ncclGinDevCommSetup)
      NCCL WARN GIN: DevComm setup failed on all available backends
  -> RuntimeError: NCCL exception (csrc/kernels/backend/nccl.cu:217): 3
The symmetric-memory GIN kernels (NCCL_SYM_GIN_KERNELS_ENABLE, default 1)
require strong signals; GDAKI does not implement them. With type 2 still in the
candidate list NCCL silently falls back to it; once type 2 is excluded there is
no backend left. Hence the pair is minimal and sufficient: exclude type 2 AND
drop the strong-signal requirement.

CORRECTION to an earlier reading of these logs: the `[Proxy Progress] Device N
CPU core M` lines are NOT a discriminator -- both arms spawn 16 of them (NCCL
creates proxy threads for ordinary collectives regardless of the GIN backend).
The "Skipping plugin ... type 2" line and the strong-signal WARN are the
evidence; the proxy-thread count is not.

Context counts printed by the type-5 arm:

    devCommCreate: creating 4 contexts

CONFOUNDS FOUND AND ELIMINATED
------------------------------
1. EP_BUFFER_DEBUG=1 is inside the timed region. csrc/elastic/buffer.hpp:1151
   builds a stringstream and printfs "CPU side received count" from inside
   dispatch's host polling loop. Measured cost: +0.7% at 8192 tok but +6-9% at
   128 tok (352.0 -> 371-385). The b200/pin launcher does not forward it, so pin
   arms were clean while official arms were penalized -- a real cross-arm
   confound. Every number in this file was taken with it OFF; the flag is now
   documented as debug-only in run_test_ep.sh.
2. First pin run silently used test_ep.py defaults (4096 tok / topk 6) because
   the b200 launcher forwards only --num-processes/--num-sms. Caught by diffing
   the `Config:` header against results/p5en_ours_20260813/repro_2n_sms12.P5-1.log
   (158 MB / 857 us vs 399.8 MB / 1504 us). Always diff the Config block.
3. Four teardown runs overwrote each other because `tr '=' ''` errors on macOS
   ("tr: empty string2"), collapsing every tag to the same name. Redone with
   explicit tag pairs. Stamp every distinguishing variable into the filename.
